## Interview Preparation: 8 Talking Points

### Talking Point 1: 5-Layer Model (All Roles)

**Question**: *"How do you think about system architecture?"*

**Answer**: 
"I think in layers. My quantum-classical OS controller uses a 5-layer model: Physical (hardware topology), Logical (circuit structure), Workflow (task scheduling), Capability (device properties), and Governance (policy enforcement). Each layer is independent — a team owns one layer without touching others.

The key insight: orthogonal concerns. The Physical layer cares about qubit connectivity; it doesn't care about job scheduling. Workflow layer schedules jobs; it doesn't care about qubit physics. Governance layer enforces policy; it doesn't care how tasks execute.

This prevents circular dependencies. It scales from 1 device to 1000. It enables enterprise governance without rewiring control systems."

**Why it works**: Every senior architect role needs to hear you think in layers. This is *the* job.

---

### Talking Point 2: Governance Without Coupling (Security Architects)

**Question**: *"How do you enforce policy at enterprise scale?"*

**Answer**: 
"Policy should be decoupled from control. In my design, governance is a *layer*, not a gatekeeper scattered through the codebase. Pre-execution, I evaluate 5 pluggable constraint checks: coupling ratios, frequency separation, bandwidth, thermal stability, interference. Each returns (is_admissible, confidence, violations).

If any check fails, the action is rejected before execution. If it passes, I log the decision and execute. Post-execution, I validate and learn.

This means: adding a new governance rule is one new check function. No need to rewrite the control loop. And every policy decision is auditable — enterprise compliance requires this."

**Why it works**: Security architects live this problem. Show you've solved it.

---

### Talking Point 3: Real-Time Feedback (Atom, PsiQuantum)

**Question**: *"How do you handle real-time constraints in quantum systems?"*

**Answer**: 
"Real-time means deterministic, not fast. My 6-stage loop has explicit timing domains. Sense and Act must be <1ms (hard real-time). Estimate can be 1-10ms (soft real-time). Constrain can be 10-100ms (nearline). Learn is offline.

The loop runs continuously: sense qubit state → estimate hidden parameters (temperature, coupling drift) → constrain next action by physics limits → act deterministically → validate execution → learn for next cycle.

Key: the action envelope (pulse, qubits, timing) is fixed-size, deterministic. No allocation in the inner loop. Every decision is justified by physics, not guesses."

**Why it works**: Startup hardware engineers live this daily. You speak their language.

---

### Talking Point 4: Constraint-Driven Design (PsiQuantum, NXP)

**Question**: *"How do you integrate with new hardware?"*

**Answer**: 
"Hardware integration is constraint integration. For neutral atoms, the constraints are trap stability, ion temperature, photon collection efficiency. For photonic systems, it's wavelength separation, coupling ratios, thermal drift, detector efficiency.

In my design, constraints are pluggable functions: `is_action_valid(action, hardware_state) → (admissible, violations)`. To support a new hardware type, I add 2-3 new constraint checks.

This scales O(N) in constraint count, not state size. And it's deterministic: every action either passes all checks or fails with reasons."

**Why it works**: Hardware-software co-design engineers need to hear this. You've solved their integration problem.

---

### Talking Point 5: Distributed Architecture (IonQ, IBM Qiskit)

**Question**: *"How does your architecture scale to distributed systems?"*

**Answer**: 
"Each quantum device has its own 5-layer graph. Networking happens at the Workflow layer — jobs route across devices, not circuits or states. This means:

- Physical layer: device-local (no networking needed)
- Logical layer: device-local (circuits compile per-device)
- Workflow layer: network-exposed (jobs route across devices)
- Capability layer: federated (each device reports capabilities)
- Governance layer: network-enforced (policy checks before routing)

This architecture means networking middleware only needs to know Workflow and Capability layers. Physical and Logical layers stay device-local. Teams can own each layer independently, even in a networked system."

**Why it works**: Distributed systems engineers love clean layer boundaries. This is a clean architecture.

---

### Talking Point 6: Observability (AWS TPM, IBM Infrastructure)

**Question**: *"How do you monitor quantum systems at enterprise scale?"*

**Answer**: 
"Observability for quantum means real-time per-layer health + per-phase metrics. My dashboard architecture:

1. RuntimeEvent: Every decision (sense, estimate, constrain, act, validate, learn) emits an event with timestamp, confidence, anomaly flags
2. GraphLayerSummary: Per-layer health (physical qubits healthy? logical circuits running? workflows scheduled? capabilities up-to-date? policies enforced?)
3. LoopStateSnapshot: Per-loop metrics (duration per phase, confidence level, anomaly count)

This is push-based (backend pushes events as they happen), not pull-based. Enterprise monitoring expects push. And it's layered — a dashboard can zoom into physical layer issues without touching governance logic."

**Why it works**: Enterprise infrastructure engineers need real-time observability. You've designed it.

---

### Talking Point 7: Team Ownership (Google Technical Lead, AWS TPM)

**Question**: *"How do you enable independent teams?"*

**Answer**: 
"Layer separation enables team separation. In a quantum company:

- Physical layer team: owns qubit connectivity, calibration, stability (talks to hardware vendors)
- Logical layer team: owns circuit synthesis, compilation, optimization (talks to customers)
- Workflow layer team: owns job scheduling, resource allocation, queueing (talks to cloud platform)
- Capability layer team: owns device profile, metadata, capability reporting (talks to all teams)
- Governance layer team: owns policy, compliance, audit (talks to enterprise customers)

Each team owns one layer. Contracts between layers are explicit (node types, edge types, validation rules). A team can rewrite their layer without breaking others.

At scale (Google, AWS), you have 50+ people in each layer. This architecture prevents coupling."

**Why it works**: Enterprise leaders need to hear about team structure. This scales to hundreds of engineers.

---

### Talking Point 8: Type Safety & Validation (All Roles)

**Question**: *"How do you prevent runtime errors?"*

**Answer**: 
"Closed enums instead of strings. My graph model uses NodeType enum (10 types), EdgeType enum (25+ types), ConfidenceLevel enum (5 levels). This means wrong node types are caught at type-check time, not runtime.

Validation rules are explicit: `validate_node(node) → (valid, errors)`. The schema is version-controlled. Tests validate the schema against golden fixtures.

This matters for quantum because: a misconfigured node (wrong qubit assignment, wrong timing domain, wrong constraint check) causes incorrect control. You want errors at type-check time, not at execution."

**Why it works**: Senior architects care about robustness. This is how you build robust systems.
